# Herdr Mobile Relay: Persistent Pairing & Architectural Runbook

This document defines the canonical origin, pairing architecture, and troubleshooting procedures for Herdr Mobile Relay (`herdr-mobile-relay`).

---

## 1. The Canonical Origin & Routing Rules

There is **exactly ONE canonical URL** for the Herdr Mobile Web PWA:

```
https://relay.yaping.dpdns.org
```

### Explicit "Never Use" List

| Origin / Address | Why It Fails | Classification |
|---|---|---|
| `http://192.168.6.129:8380` | **Insecure Context (Plain HTTP)**: Modern mobile browsers disable `window.crypto.subtle` on non-localhost plain HTTP origins. The relay client (v0.22.6+) cannot derive encryption keys or perform E2EE handshakes over insecure HTTP. | **BANNED** |
| `https://herdr.yaping.dpdns.org` | **Wrong Hostname**: This DNS name points to the SSH-bridge reverse proxy / web gateway service, NOT the Herdr Mobile Relay daemon. Opening the PWA here will fail to connect to local relay WebSockets. | **BANNED** |
| `http://127.0.0.1:8380` | Loopback only. Valid for local curl/healthchecks on Mac, unreachable from mobile devices. | Internal Only |

---

## 2. Root Cause Analysis: Why "0/0 Relays" Kept Recurring

1. **Origin-Scoped `localStorage` Partitioning (R1)**:
   - Web browsers strictly isolate `localStorage` by scheme + hostname + port.
   - Opening `http://192.168.6.129:8380`, `https://herdr.yaping.dpdns.org`, and `https://relay.yaping.dpdns.org` creates **three completely independent localStorage partitions**.
   - When the user opened an unconfigured or different hostname in their mobile browser, the PWA initialized with an empty relay array (`[]`), displaying `"0/0 relays"` / `"Waiting for relays"`.

2. **Ephemeral Bootstrap Invitation Expiry (R2)**:
   - The interactive pairing flow (`kill -USR1 <pid>`) generates an ephemeral bootstrap invitation stored in `devices.json` with a 10-minute expiry (`expires_at`).
   - If a new browser tab or origin attempted to pair outside that 10-minute window, pairing was rejected.

3. **Wrong Host in Server Origin Metadata (R3)**:
   - Server-side origin files (`phone-app-origin` and `phone-app-origin-configured`) previously recorded `https://herdr.yaping.dpdns.org`.
   - This caused setup links generated by the server to point to the SSH-bridge rather than the relay.

4. **LaunchAgent Environment Decoupling (R4)**:
   - LaunchAgent previously relied on external environment files that could occasionally race during startup, triggering `"refusing to bind tokenless relay to non-loopback address 0.0.0.0"`.
   - Permanent fix: LaunchAgent plist now directly embeds `HERDR_RELAY_TOKEN` and `HERDR_ALLOW_TOKENLESS_NON_LOOPBACK=false` inside `EnvironmentVariables`.

## 3. Pairing Persistence Model (Device Enrollment, NOT Token-Only)

### ⚠️ The token-only setup URL is NOT permanent

Under `herdr-e2ee-v2`, pairing requires **server-side device enrollment**: the phone generates a device keypair and the relay enrolls that credential in `devices.json`. The `setup-fragment` URL (token-in-hash form below) only seeds the *relay URL + auth token* into `localStorage` — it does **not** enroll a device credential.

```
https://relay.yaping.dpdns.org/#label=MacBook-Neo&relay=https%3A%2F%2Frelay.yaping.dpdns.org&setup=<token>
```

Because no device credential is enrolled by that link alone, the setup URL does **not** survive storage loss. This was proven by a controlled experiment on the phone: after wiping the browser app data, re-opening the saved token-only setup link did **not** restore pairing. The relay server responded verbatim:

> `MacBook-Neo refused this device. Import a new invitation link.`
>
> `This computer refused this device. Import a new invitation link, or remove and add the relay.`

The cause is `device_unauthorized`: wiping app data generates a brand-new device keypair, which is not present in the relay's enrolled device store, so the handshake is refused until a fresh bootstrap invitation is armed.

### What "durable" actually means

The genuinely durable state is the **combination** of:

1. **A PWA home-screen shortcut pinned to the canonical origin** `https://relay.yaping.dpdns.org` (this fixes origin wandering and isolates `localStorage` from URL-bar edits), and
2. **Intact browser storage** holding the enrolled device credential.

As long as the browser app data is **not** cleared, the PWA reconnects forever on every launch — the healthy steady state reads:

```
1/1 relays · 5
```

If the app data **is** cleared, or you move to a new device, the previously saved link cannot re-enroll. **This is the designed flow, not a bug**: run `herdr-relay-pair` once (see §5) and re-add the relay a single time. After that, it persists again under rule (1)+(2) above.

### Canonical Origin & Banned Addresses (unchanged)

There is exactly ONE canonical URL for the PWA:

```
https://relay.yaping.dpdns.org
```

| Origin / Address | Why It Fails | Classification |
| --- | --- | --- |
| `http://192.168.6.129:8380` | **Insecure Context (Plain HTTP)**: mobile browsers disable `window.crypto.subtle` here, so E2EE handshakes cannot derive keys. | **BANNED** |
| `https://herdr.yaping.dpdns.org` | **Wrong Hostname**: points to the SSH-bridge reverse proxy, NOT the relay daemon. The PWA cannot reach relay WebSockets here. | **BANNED** |
| `http://127.0.0.1:8380` | Loopback only; valid for Mac-local healthchecks, unreachable from mobile. | Internal Only |

### Method A: Installing as a Standalone PWA (binds the origin)

1. Open `https://relay.yaping.dpdns.org` in the mobile browser (after a successful enroll, see §5).
2. Tap the browser menu (**⋮** on Chrome / Android, or Share on Safari / iOS).
3. Tap **"Add to Home Screen"** or **"Install App"**.
4. Launch exclusively from the Home Screen icon. This pins the standalone PWA to `https://relay.yaping.dpdns.org` and keeps its `localStorage` isolated.

### Method B: Generating a Bootstrap Invitation QR on macOS (for first enroll)

The interactive pairing flow arms an ephemeral bootstrap invitation (`kill -USR1 <pid>` or the `herdr-relay-pair` helper). Use the printed `wss://` URL + key to enroll a *new* device:

```bash
# re-arm bootstrap and print a fresh invitation (token shown on screen, not committed)
herdr-relay-pair
```

> Note: the bootstrap invitation carries the relay auth `<token>` and expires per the server's `expires_at` window. It exists only to perform the one-time device enrollment; afterwards persistence is governed by §3 rule (1)+(2).


## 4. Disaster Recovery (cleared data / new device / "0/0 relays")

If the phone shows `0/0 relays`, `Waiting for relays`, or a refused-device message after app-data wipe or a fresh device:

1. **On the Mac**, re-arm the bootstrap and print a fresh key:
   ```bash
   herdr-relay-pair
   ```
   It re-arms the bootstrap invitation and prints the relay URL + key (`<token>`).
2. **On the phone**:
3. The relay reconnects and returns to the durable `1/1 relays · 5` steady state.

This one-time re-enroll is the intended recovery path — not evidence of a broken pairing system.


## 5. Never Do This (what causes `0/0 relays`)

- **Never clear the browser app data / "site data" for the relay PWA.** This wipes the enrolled device credential and forces a `device_unauthorized` refusal. App-data wipe is the single most common cause of `0/0 relays`.
- **Never open the PWA from a different origin** (`http://192.168.6.129:8380`, `https://herdr.yaping.dpdns.org`, or any LAN IP). Each origin is a separate `localStorage` partition with an empty relay array.
- **Never rely on the saved token-only setup link to survive a wipe.** It re-seeds the URL+token but cannot re-enroll a device credential (see §3 warning).
- **Never commit a real token.** Use `<token>` placeholders only; real keys come from `herdr-relay-pair` output at runtime.

## 6. Diagnostics & Health Check Runbook

When diagnosing relay issues on the Mac:

### 6.1 Verify Relay Daemon Health
```bash
curl -s http://127.0.0.1:8380/healthz | jq .
```
Expected output:
- `"status"`: `"ok"`
- `"readiness"`: `"ready"`
- `"instance"`: `<STATIC_INSTANCE_ID>` (e.g. `8893338e2ba47e46cd9fe816d31fc48d`)

### 6.2 Verify Process & Network Bind
```bash
pgrep -fl herdr-mobile-relay
lsof -i :8380
```
The relay MUST listen on `*:8380` (or `0.0.0.0:8380`), bound by `launchd`.

### 6.3 Check LaunchAgent Status
```bash
launchctl print gui/$(id -u)/com.steven.herdr-mobile-relay | grep -E 'state|pid|runs'
```

### 6.4 Restarting the Relay (If Ever Required)
```bash
launchctl kickstart -k gui/$(id -u)/com.steven.herdr-mobile-relay
```
*Note: Restarting drops active WebSocket clients. Avoid restarting while an active mobile session is in use.*

### 6.5 Inspect Device Auth Store
Inspect enrolled devices without leaking full secrets:
```bash
python3 -c '
import json
with open("/Users/steven/.config/herdr/plugins/config/herdr-mobile-relay.events/device-auth/devices.json") as f:
    d = json.load(f)
print("Enrolled controllers:", len(d.get("credentials", [])))
for c in d.get("credentials", []):
    print(f"  - [{c.get(\"name\")}] id={c.get(\"device_id\")} paired={c.get(\"paired_at\")} last_seen={c.get(\"last_seen_at\")}")
'
```
